## Project state

The app is an Expo Router + TypeScript project, Android only, dark UI by default (Light or System in Settings). `app/` holds routes only (the full route table, with params, is in `docs/ARCHITECTURE.md`): `_layout.tsx` runs migrations + seed and preloads the text and icon fonts behind the splash screen, initializes i18next in the stored language, and renders either the first-launch `LanguagePickerGate` or the `Stack`, inside a `ThemeProvider`; `(tabs)/` has the three tabs Workout · Exercises · Profile (`expo-router/js-top-tabs` with the bar at the bottom, a native pager: tabs switch by swiping sideways; headers are off, each screen draws its title through `Screen`); every other screen is a root `Stack` route above the tabs (active workout, pickers, editors, History, Settings, tactical board, details). The Workout tab lists the routines as chips with the selected one's workout cards; a routine moves left/right only through its menu. The Exercises tab is search + six category cards (the five categories plus Custom; New Exercise is a `+` in the header). ## What this app is

Basket Routine: an Android-only, personal-use app (sideloaded APK, no Play Store) for logging basketball training routines. It follows Hevy's user flow (routines → workout templates → active workout → history) but tracks **Attempts / Makes** per set with automatically derived FG% instead of weight/reps.

## Domain model (conceptual)

- **Routine** → **Workout (template)** → **Exercise (catalog)**, referenced by a **Workout exercise** entry with a **Template set** list.
- Every exercise has a `trackingType`: `makes_attempts` (FG% applies) or `check` (done/not-done), extensible later to reps/time.
- For `makes_attempts`, the workout exercise has a `targetMode` shared by all its sets: `makes` (fixed makes, user logs attempts) or `attempts` (fixed attempts, user logs makes).
- **Session** is a snapshot created when a template (or an empty workout) is started — it copies exercise name/category/trackingType/targetMode so history survives catalog edits, and never mutates the template it came from. At most one `in_progress` session at a time.
- **Validation invariant**: makes can never exceed attempts (in `attempts` mode, logged makes ≤ target; in `makes` mode, logged attempts ≥ target).
- **FG% is always derived, never stored**: set FG% = makes/attempts; aggregate FG% = Σmakes/Σattempts (not an average of percentages); only sets with a logged value count.
- A workout exercise (template or session) can have one optional **tactical board**, stored as JSON on the row and copied into the session like the rest of the snapshot.
- The **profile** (name, photo) lives outside the schema, in `expo-sqlite/kv-store`.
- **Deletion is soft for the catalog and templates** (routines, workouts, custom exercises): user-facing delete sets `archivedAt`, hiding the record while sessions keep their snapshot, so history stays intact. **Sessions are hard-deleted** (cascading to their exercises and sets): deleting a finished session from History (`deleteFinishedSession`), discarding the workout in progress, and removing an exercise or a set during a workout. Deleting a custom exercise also hard-deletes its entries from templates (`archiveCustomExercise`).

## Working conventions

- One commit per finished feature or change, not per internal step. Fix-up commits are fine afterward if CI or a build fails.
- **Tests**: write or update a test only when the component, function or behavior it covers is new or changed. No tests for thin wrappers whose behavior the flow tests already exercise (`expectAccessibleControls` also guards their role and name), none that restate the implementation (token values, style numbers that are the code itself), none that check a mock. Find things by role, label or text; use a `testID` only where there is no accessible name (a media view, a stat value next to other numbers).
- Nothing gets installed (global tools, SDKs, version managers) without asking first and explaining what it's for.
- Code, comments and docs are in English throughout, regardless of the developer's own language. Every user-facing text (labels, accessibility labels, alerts) goes only through `src/i18n/`'s dictionaries, never a string literal in a screen or component.

```
    settings/         # idioma (código, storage no kv-store, seletor de idioma no primeiro acesso, Settings)
    tacticalBoard/    # prancheta tática (meia quadra em SVG) e seu editor
  components/         # componentes base de UI, haptics, hooks de teclado
  theme/              # tokens: cores, fontes, tipografia, espaçamento
  test-utils/         # expectAccessibleControls()
scripts/              # utilitários de linha de comando (optimize-exercise-media.sh: GIF/vídeo → MP4 vertical leve, precisa de ffmpeg)
media-source/         # onde soltar os GIFs/vídeos originais dos exercícios; o script grava em media-source/optimized/ (conteúdo ignorado pelo git)
__tests__/            # testes de fluxo com renderRouter (um por área)
assets/               # fontes, ícone/splash, mídia de exercícios e imagens de categoria
docs/                 # design.md, backlog.md, ARCHITECTURE.md, archive/ (planos antigos, só histórico)
.github/workflows/    # ci.yml e build-apk.yml
```

Arquivos-chave:

- `app/_layout.tsx`: entry point da UI; prepara o banco e as fontes atrás da splash e declara as rotas do Stack.
- `app/(tabs)/_layout.tsx`: as três abas, a `TabBar` e o `ResumeBanner`.
- `src/db/schema.ts`: modelo de dados (rotinas, workouts, templates, exercícios, sessões e sets).
- `src/db/repositories/*.ts`: todas as consultas e escritas no SQLite; lançam `DomainError`.
- `src/features/dataStore.ts`: store único; toda escrita passa por um `actions.ts` que o notifica.
- `src/domain/validation.ts` e `src/domain/fg.ts`: invariantes de makes/attempts e o cálculo de FG%.
- `src/theme/colors.ts` + `src/theme/spacing.ts`: os únicos lugares com valores de cor e tamanho.
- `src/i18n/translations/en.ts` + `pt-BR.ts`: os dois dicionários, com as mesmas chaves (checado por `parity.test.ts`); `src/i18n/i18n.ts` inicializa o i18next no idioma salvo, antes da primeira renderização.
- `jest.setup.js`: mocks dos módulos nativos para o Jest (inclui o `expo-sqlite/kv-store` em memória e a inicialização do i18next em inglês).
- `app.json` / `eas.json`: config do Expo (ID Android imutável) e perfis do build do APK.
- `drizzle.config.ts`: de onde o `db:generate` lê o schema e para onde gera as migrations.

## Onde encontrar

- Para adicionar uma rota → crie o arquivo em `app/`; se for tela sobre as abas, registre em `app/_layout.tsx`; se for aba, em `app/(tabs)/_layout.tsx` (e `src/components/TabBar.tsx`).
- Para alterar o banco → `src/db/schema.ts`, depois `npm run db:generate` (nova migration em `src/db/migrations/`, nunca editar as existentes).
- Para uma nova consulta/escrita → `src/db/repositories/` e a ação correspondente em `src/features/<área>/actions.ts`.
- Para uma regra de negócio → `src/domain/` (puro, com teste ao lado).
- Para os exercícios predefinidos → `src/db/seed/exercises.ts`; a mídia deles em `assets/exercises/` + `src/features/exercises/seedMedia.ts` (originais em `media-source/`, reduzidos por `scripts/optimize-exercise-media.sh`).
- Para cores, fontes e espaçamento → `src/theme/` e `docs/design.md`.
- Para um componente de UI reutilizável → `src/components/`.
- Para autenticação → não existe: o app é local, de um único usuário e sem servidor; o perfil fica em `src/features/profile/profileStorage.ts`.
- Para um texto novo na UI → adicione a chave em `src/i18n/translations/en.ts` **e** `pt-BR.ts`, e use `t('...')` (via `useTranslation()` ou, fora de componentes, `i18n.t`); nunca um literal em inglês direto na tela.
- Para o idioma → `src/features/settings/` (código, storage, `setLanguage`, `useLanguage`); o seletor, exibido no primeiro acesso (e a cada abertura só em desenvolvimento), é `LanguagePickerGate.tsx`, usado em `app/_layout.tsx`.
- Para testes → unitários ao lado do código; fluxos em `__tests__/`; banco em memória com `src/db/test-utils.ts`; mocks em `jest.setup.js`.
- Para CI e build do APK → `.github/workflows/` e `eas.json`.
- Para o que falta fazer → `docs/backlog.md`; para saber por que algo foi decidido → `docs/archive/`.

Ao criar, mover ou remover diretórios/arquivos principais, atualize o Mapa do Projeto.
